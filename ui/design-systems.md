# Design systems and visual direction

The project owns its brand, tokens, components and platform conventions. dkstack sets the quality rules.

## Choose the direction

1. Read the existing screens, tokens, styles, components and project requirements.
2. If a complete visual system exists, follow it. Do not add a second palette or component style.
3. If the system is partial, extend it in the same style. Record each new token or component where the project keeps design decisions.
4. If no visual direction exists, choose one for the product, the audience, the platform and the task. State the reason. Keep each decision small and easy to change.
5. Ask the owner only when two choices change the brand or the product identity. Ask only if the requirements do not decide.
6. A redesign request allows exploration. It does not allow work outside its scope.

## Defaults

A default on the ui/ pages applies when the project has no design system, or when the project's system does not cover that area. The project's system wins over the Defaults sections only. The other rules on the ui/ pages still apply, including each rule marked "(dkstack rule)". To differ from one of them, record an exception as [Precedence](../AGENTS.md#precedence) says.

Do not copy the look of one product. Do not use the generic patterns in [visual design](visual-design.md#generic-patterns). Keep accessibility and usability for each visual choice.
